# Changelog

All notable changes to the **Saldai (Monorepo)** project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).


## [Unreleased]
### Changed
- **Mobile**: los campos de texto unificados en un solo `Input`, el aviso del código de 6 dígitos, la app agrupada por feature, los imports al alias `@/`, los mocks a `services/mocks/`, la caché y el alta optimista con react-query, los colores y medidas desde los tokens, los identificadores alineados con la marca y las dependencias declaradas. El detalle está en [`mobile/CHANGELOG.md`](mobile/CHANGELOG.md).
- **CI también corre en los PR hacia `main`**: el workflow se disparaba solo en `development`, así que un PR de release no traía ningún check propio — mostraba el run verde del tip de `development`, que es el mismo commit pero no es lo mismo que haberlo verificado contra `main`. Se vio en el release #59. Para que el check sea obligatorio ahí hace falta además agregarlo al ruleset de `main` desde la interfaz de GitHub.
- **`api/server.js` queda en 13 líneas**: era un archivo de 213 que mezclaba el arranque del proceso, el CORS, las cuatro rutas de gastos, los dos health checks, la validación de cada parámetro y las consultas a Supabase. Ahora `server.js` solo carga la config y abre el puerto; la app se arma en `src/app.js`, las rutas quedan en `src/rutas/{gastos,salud}.js`, las consultas en `src/gastos/repositorio.js` (que es donde se traduce entre el contrato HTTP y los nombres de la tabla) y la validación de parámetros en `src/gastos/validacion.js`, como funciones puras. Separar la app del `listen()` es lo que permite montarla en un test y pegarle a una ruta de verdad: la API pasó de 8 tests a 18, incluidos los que verifican que `/gastos/parsear` parsea sin sesión, que un input que el parser rechaza responde 422 y no 400, y que las tres rutas protegidas responden 401 antes de tocar la base.
- **`gastos.fecha` es `date` y no text**: guardarla como `DD/MM/AAAA` impedía filtrar y ordenar por fecha. La migración convierte los datos existentes y agrega el índice `(user_id, fecha desc)`. La API devuelve `fecha` en ISO (`AAAA-MM-DD`) y agrega `fechaFormateada` (`DD/MM/AAAA`) para mostrar, igual que `monto` y `montoFormateado`.
- **Prioridad de categorías**: Mercado se evalúa antes de Básicos para que "acuenta" (supermercado) no caiga en "cuenta".
- **Keywords**: agregadas `metrogas`, `lipigas`, `abastible` (Básicos) y `apple tv` / `appletv` (Suscripciones).
- **Validación de entorno**: nuevo `api/src/config.js`. La API no arranca si faltan `SUPABASE_URL` o `SUPABASE_ANON_KEY`, y avisa por consola cuando falta una variable opcional. Los orígenes de CORS se filtran, así que ya no se registran entradas `undefined`.
- **Middleware de autenticación**: `auth.js` pasó de `import/export` (ESM) a CommonJS, igual que el resto de la API. Deja de depender de la versión de Node que elija el host.
- **Versión de Node fijada**: `engines: node >=22 <23` en la raíz y en `api/`, más `.node-version` para Render.
- **`.gitignore`**: reescrito. Era una plantilla de Python en un monorepo de JavaScript (ignoraba `__pycache__`, `*.egg-info`, `.pybuilder/` y hasta `.git/`). Ahora está agrupado por tema y solo ignora lo que corresponde.
- **Un solo lockfile**: `package-lock.json` de la raíz se versiona (es el del monorepo y lo que hace reproducible `npm ci`) y se ignoran los de cada workspace. Antes el `.gitignore` decía ignorarlos todos, pero el de la raíz estaba versionado igual.
- **Políticas RLS existentes**: acotadas al rol `authenticated` (antes `public`, que incluye `anon`) y con `auth.uid()` envuelto en `(select ...)`, que es lo que pedía el advisor de performance de Supabase.
- **Un CHANGELOG por salida, con formato verificado**: el de `mobile/` lleva el detalle de la app (es el que alimenta las notas de versión de las stores), el de la raíz lo transversal al monorepo, y `web/` arranca el suyo para cuando se retome. Los tres declaran el formato de Keep a Changelog —`## [x.y.z] - AAAA-MM-DD` y debajo solo `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed` o `### Security`, una vez cada una— y lo verifica `npm run changelog:check` en CI, sobre el archivo entero. En la raíz, las dos secciones `### Changed` que un merge dejó dentro de `[Unreleased]` se unieron en una.
- **`mobile/CHANGELOG.md` quedó dentro del formato y al día**: se había escrito meses sin formato —versiones fuera de orden, siete secciones repetidas dentro de una misma versión, `\n` literales en vez de saltos de línea y un segundo encabezado `# Changelog` con su preámbulo en medio del archivo— y además estaba congelado en abril, así que el archivo que alimenta las stores no servía para redactar un release. Se reordenó una vez, por pedido explícito: las versiones quedaron de la más nueva a la más vieja, cada una con una sola sección de cada tipo, los `\n` convertidos en saltos de línea y el encabezado duplicado eliminado. **No se inventó ninguna fecha ni ninguna versión**: las que ya estaban escritas coinciden con el historial de git y alcanzaban para ordenar el archivo. **No se reescribió el texto de ninguna entrada**; lo único que se movió de versión es el bloque de OTP que estaba repetido en `[1.5.6]`, que corresponde al commit del 11 de abril y quedó en `[1.5.5]`, su versión. El detalle de mobile de #61 a #70 se movió acá desde el `[Unreleased]` de la raíz, tal como estaba escrito, y en la raíz quedó un puntero por sección.
- **El check "Formato de los CHANGELOG" existe de verdad**: el ruleset de `development` y `main` lo exige por nombre, pero era un paso dentro del job "Tests, lint y tipos", y un paso no reporta un check con su nombre. El check quedaba exigido y nunca llegaba, así que GitHub mostraba todo PR como bloqueado aunque CI estuviera verde — pasó en los PR #70, #71 y #72. Ahora es un job propio con ese nombre exacto, y no instala dependencias porque `scripts/verificar-changelogs.mjs` solo usa módulos de Node. Es el mismo tipo de falla callada que los globs de Tailwind: una configuración que enumera nombres y deja de encontrarlos cuando el otro lado se mueve.
- **`mobile/CLAUDE.md` dice cuándo hace falta un build nuevo**: qué obliga a un binario nuevo (una dependencia con código nativo, las claves de `app.json` que tocan el binario, un salto de SDK), qué no (JS, TS, estilos, tokens, assets ya referenciados, y el `.env`, que solo pide `start:clear`) y por qué un build local compila en minutos donde EAS tarda parejo. Estaba explicado en un documento fuera del repo.

### Added
- **`docs/aprendizajes.md`**: las veces que algo de este stack no se comportó como se esperaba, versionadas. Los aprendizajes se venían dejando en un `REPORT.md` en la raíz que está en el `.gitignore` —así que ningún hilo lo ve—, quedó congelado el 13 de abril y describe la estructura de carpetas anterior al PR #57, de manera que hoy desorienta más de lo que ayuda. El archivo nuevo tiene tres reglas: se escribe **solo cuando algo sorprendió** (estaba roto y no daba error, o la causa no era la obvia) y no una entrada por PR; cinco puntos fijos y cortos (síntoma, causa, por qué no se notaba, arreglo, regla) sin logs de comandos, que es lo que hundió al REPORT; y lo escribe el hilo que resolvió el problema, en el mismo PR del arreglo. Arranca con seis entradas: los globs de Tailwind del #60, el `req.user.sub` del #46, `express-async-errors` sin manejador detrás, el plugin viejo de Babel de NativeWind v4, los colores en HSL por los componentes tipo Shadcn y los paddings de Figma que se mapean a tokens. Los aprendizajes portables siguen yendo al documento vivo de la auditoría, no acá. El `REPORT.md` no se tocó: es un archivo de crim.
- **Mobile**: la "x" para limpiar un campo, la categoría sugerida mientras se escribe, las categorías y el selector de método apagados en la v1, el build instalable de `preview`, el `.env.example`, el development build con EAS, los atajos para revisar sin rebuildear, los dos APK conviviendo en el teléfono y los iconos del diseño. El detalle está en [`mobile/CHANGELOG.md`](mobile/CHANGELOG.md).
- **Cabeceras de seguridad y límite de pedidos en la API**: `helmet` pone las cabeceras que faltaban (`nosniff`, `X-Frame-Options`, HSTS, `Referrer-Policy`) y saca el `X-Powered-By: Express`, que le decía a cualquiera con qué está escrita la API. `express-rate-limit` acota los pedidos por minuto y por IP, con cupos separados por ruta: `POST /gastos/parsear` es el único endpoint sin sesión, así que cualquiera podía llamarlo en loop y quemar el CPU compartido del plan gratis de Render. `/health/db` también se limita, porque tampoco pide sesión y además consulta Supabase; `/health` no, porque es el keep-alive que evita que Render duerma el servicio. La app declara `trust proxy`: sin eso `req.ip` es la del proxy de Render y todos los clientes comparten un mismo cupo. El cuerpo del request pasa de los 100kb que trae `express.json()` por defecto a 10kb, que para una línea de texto ya es holgado.
- **Reporte de errores con Sentry, opcional**: un 500 en producción existía solo en el log de Render, que se mira cuando alguien ya se dio cuenta de que algo anda mal — que es exactamente cómo el bug de auth pasó seis meses sin que nadie lo viera. Es opcional a propósito: sin `SENTRY_DSN` la API arranca igual, no se carga el paquete y no se manda nada a ninguna parte, así que local y los tests quedan iguales. No reporta datos de la persona (`sendDefaultPii: false`), porque el cuerpo del request trae el gasto que escribió y eso no hace falta para leer un stack trace.
- **El parser vive en `@saldai/core`**: `parsearGasto` y el parseo de fechas humanas ("ayer", "lunes", "15/02") salieron de `api/` y ahora son parte del dominio compartido, así que mobile puede parsear sin pasar por la red. La zona horaria se le pasa como argumento en vez de leerse de `APP_TIMEZONE` dentro del dominio: la API la resuelve en `src/config.js` y el CLI con la variable de entorno, y el core asume Chile si nadie la pasa.
- **Tipos compartidos del contrato de la API** en `packages/core/index.d.ts`: `Gasto`, `GastoParseado`, `Metodo`, `Categoria`, `FechaISO` y las respuestas de cada endpoint. Mobile los declaraba por su cuenta, con `fecha` y `categoria` como `string` suelto, y de ahí venían errores como leer `error` en singular cuando la API responde `errores[]`. Al tiparlo de verdad aparecieron dos lugares donde el método de pago era un `string` cualquiera.
- **`@saldai/core`**: paquete nuevo con el dominio compartido, sin framework y sin red: el catálogo de categorías y su regla de match, los métodos de pago, el formato de montos en pesos y las conversiones y rangos de fechas. Lo consumen la API y mobile (y web cuando le toque), así que un gasto significa lo mismo en todas las salidas. 23 tests propios; `npm test` en la raíz ahora corre los del core y los de la API.
- **Tests del parser (API)**: Suite real con `node:test` en `api/test/` (41 casos) para `parser`, `categorizer` y `dateParser`. `npm test` ahora corre los tests; la demo con salida en colores quedó como `npm run demo`.
- **Scripts en la raíz**: `npm run lint` (web) y `npm run typecheck` (mobile), además del `npm test` que ya estaba. Es lo que va a correr CI.
- **Migraciones de Supabase versionadas** (`supabase/migrations/`): hasta ahora el schema se editaba a mano desde el dashboard y el proyecto no tenía ninguna migración registrada. Incluye un baseline del estado actual de `public.gastos`.
- **`public.delete_user()`**: la pantalla de configuraciones llamaba esta función para borrar la cuenta, pero nunca existió. Borra los gastos y la cuenta del usuario de la sesión, con `security definer` acotado.
- **Políticas RLS de UPDATE y DELETE** en `public.gastos`: la tabla solo tenía SELECT e INSERT, así que editar o borrar un gasto fallaba en silencio.
- **Índice `(user_id, creado_en desc)`** en `public.gastos`: la tabla solo tenía el índice de la primary key, y ninguna consulta de la app busca por id.
- **Los `CLAUDE.md` se versionan**: `CLAUDE.md` estaba en el `.gitignore`, así que la única guía del repo era `mobile/CLAUDE.md` en la máquina de crim — una sesión que corre en otra parte no la veía, y la que la veía leía el stack de hace dos reorganizaciones: la API en Railway, los íconos como `@expo/vector-icons`, `contexts/` y `hooks/` que ya no existen, endpoints sin `anio` y los colores como hex a mano cuando hoy hay una capa semántica de tokens. Ahora hay un `CLAUDE.md` en la raíz con lo transversal (los cinco workspaces y qué hace cada uno, el contrato de la API, qué rama despliega cada entorno, qué archivos son generados, las convenciones del repo) y `mobile/CLAUDE.md` reescrito contra el código actual: agrupación por feature, react-query y sus llaves de caché, el alias `@/`, las variantes dev/preview, los flags de producto y los tokens por nombre semántico. El criterio para decidir qué va en estos archivos es que se pueda verificar leyendo el código: lo que es una decisión de producto o una preferencia de trabajo no entra acá. `GEMINI.md`, `REPORT.md`, `ai-setup/`, `design/`, `.claude/` y `.env` siguen fuera del repo.

### Fixed
- **Mobile**: el teclado que tapaba el form de captura, el título de login en blanco, el menú y los botones sin estilos, el temporizador vivo de la captura, los mocks con categorías y montos inventados, el selector de método en el playground, los nombres de los meses duplicados, el `expo-updates` del build de desarrollo, los errores de la API que no se mostraban, el typecheck que no cubría nada y el borrado de cuenta que fallaba en silencio. El detalle está en [`mobile/CHANGELOG.md`](mobile/CHANGELOG.md).
- **La API no tenía manejador de errores**: `express-async-errors` estaba instalado y requerido, pero no había ningún middleware de error detrás, así que un `throw` inesperado caía al handler por defecto de Express, que responde **con el stack trace en el cuerpo** cuando `NODE_ENV` no es `production`. O sea que lo que veía el cliente ante una excepción dependía de una variable de entorno en vez de ser una decisión. Ahora el cliente recibe siempre un 500 genérico, el detalle va al log, y un cuerpo demasiado grande o un JSON roto responden 413 y 400 en vez de un 500. También se agregó el 404, que antes devolvía el HTML del handler por defecto en vez de la forma `{ ok, errores, datos }` que usa el resto de la API.
- **Ningún gasto se podía guardar ni leer desde el 12 de abril**: `server.js` identificaba al usuario con `req.user.sub`, pero `supabase.auth.getUser()` devuelve el id en `user.id` y no tiene campo `sub` (`sub` es el claim del JWT, que es lo que se usaba antes de `c91652e`). Las tres consultas autenticadas salían con el string `"undefined"` como `user_id` y Postgres las rechazaba con `invalid input syntax for type uuid`, que la API reportaba como "Error al leer de base de datos". El id ahora se resuelve una sola vez en el middleware, se expone como `req.userId`, y si falta corta el request con 401 en vez de llegar a la query. La última fila de `gastos` es del 11 de abril, un día antes del commit que lo rompió.
- **`GET /gastos?mes=` mezclaba años**: el filtro era `fecha ilike '%/10/%'`, que devolvía octubre de todos los años. Ahora `fecha` es una columna `date` y el filtro es un rango `[primer día del mes, primer día del siguiente)`. El endpoint acepta `anio` opcional y, sin él, asume el año en curso.
- **Monto con sufijo k**: `12.5k` se leía como 125.000 y `1.5k` como 15.000. Con sufijo `k` el punto o la coma son separador decimal, así que ahora son 12.500 y 1.500.
- **Categorización por palabra completa**: `gaseosa` caía en Básicos por contener "gas" y `barbería` en Ocio por contener "bar". El match ahora es por palabra completa, sin acentos y aceptando el plural ("auriculares" matchea "auricular").
- **Fechas inválidas**: `31/02` guardaba otro día en silencio. Ahora devuelve error y el gasto no se parsea.
- **Zona horaria**: el "hoy" se calcula en `America/Santiago` (configurable con `APP_TIMEZONE`) y no en UTC, así un gasto cargado a las 22:00 en Chile ya no quedaba con la fecha del día siguiente.
- **Health check de base de datos**: `GET /health/db` usaba una variable `supabase` inexistente y siempre respondía 500 sin llegar a la base. Ahora crea un cliente anónimo (`createAnonClient`) y la consulta sí viaja a Supabase.

### Removed
- **Endpoint `POST /test-email`**: cualquier usuario autenticado podía enviar correos arbitrarios desde la cuenta de Resend del proyecto. El servicio `src/services/email.js` se mantiene para uso interno.


## [1.7.2] - 2026-04-12
### Changed
- **Dependencias API**: Refactorizado el middleware de autenticación (`auth.js`) para utilizar el SDK nativo de Supabase (`supabase.auth.getUser`) en la validación de tokens JWT en lugar del método manual usando llaves públicas.
- **Manejo de Errores Async (API)**: Integrado `express-async-errors` en el archivo raíz de Express 4 para garantizar que el runtime intercepte rechazos no cacheados en las promesas y evite timeouts en la base de datos.

### Removed
- **Validadores de Tokens**: Desinstalados `jsonwebtoken` y `jwks-rsa` de la API.

## [1.7.1] - 2026-04-11
### Added
- **Componentización de Autenticación**: Nuevos componentes reutilizables `EmailVerificationInput` y `OtpVerification` compartidos entre los flujos de inicio de sesión y cuenta.
- **Validación de Correo**: Función global `isValidEmail` integrada para restringir acciones (botón "Enviar código") hasta que el formato introducido sea válido.

### Changed
- **Refactorización de Verificación (OTP)**: UX alineada entre `login.tsx` y `cuenta.tsx`. Eliminado el botón "Usar otro correo".
- **Refactorización de Alertas (`Alert`)**: Implementado soporte `inline` para mostrar notificaciones críticas embebidas bajo campos de texto o botones en lugar de usar posición flotante absoluta.
- **Notificaciones de Éxito (`Notification`)**: Modificados los comportamientos en el reenvío de OTP para presentar notificaciones tipo "toast" en vez de las alertas previas. Se ajustó el sistema para no fijar alturas forzadas que causaban cortes tipográficos (clipping text).
- **Iconografía**: El icono de espera al solicitar un código temporal en campos de email cambió a blanco para mantener consistencia visual global.

## [1.7.0] - 2026-04-07
### Added
- **Integración de Emails**: Servicio de envíos configurado en la API vía Resend (`api/src/services/email.js`).
- **Endpoint de Prueba de Email**: Añadido endpoint protegido `POST /test-email` en el backend para validaciones rápidas.

### Changed
- **Rebranding Completo**: Renombrado global del proyecto de "Expense Tracker" a "Saldai".
- **Workspaces**: Actualización masiva de nombres de paquetes internos (`@saldai/ui`, `saldai-api`, `saldai-web`, `saldai-mobile`).
- **Configuración Móvil**: Actualización del package bundle a `com.crirun.saldai` y el nombre de la app.
- **Configuración Web**: Actualización de Metadata a "Saldai" en Next.js.
- **Backoffice**: Remitente de email de Resend actualizado.

## [1.6.0] - 2026-04-02
### Added
- **Soporte de Autenticación**: Nuevo sistema de Auth middleware (`/api/src/middleware/auth.js`) integrado para proteger las rutas de gastos y categorías.
- **Flujo de Acceso Móvil**: Nuevas pantallas `login.tsx` y layouts en la app para soportar el flujo Supabase OTP.

### Changed
- **Base de Datos y API**: Refactorizado `supabase.js` para crear el cliente con los tokens provistos por el cliente en cada request, respetando RLS.
- **Mobile Context**: Actualizado `GastosContext` y `AuthContext` para interceptar validaciones de estado y limpiar la data local al desconectarse.
